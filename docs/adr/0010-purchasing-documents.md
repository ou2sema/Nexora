# ADR-0010 — Purchasing documents

- **Status:** accepted
- **Date:** 2026-10-31
- **Deciders:** product owner, engineering

## Context

Phases 6 and 7 produce purchase orders and purchase returns, but the only way to hand a
document to a supplier is a screenshot or a copy of the JSON. Operators need a printable,
numbered document that matches the data the ledger already moved. The temptation is to model
a separate document archive with stored snapshots, but that duplicates every field and drifts
from the order tables the moment anything is corrected.

Phase 8 renders a purchase order and a purchase return note as PDFs from the existing tables,
on demand, inside the caller's tenant transaction. No schema change, no stored files.

## Decisions

### 1. Documents are rendered on demand from tenant-scoped reads

`PurchaseDocumentsService` reads the organization, the order or return, its lines, the
supplier, the warehouse and the location inside `TenantAccessService.runAsMember`, then hands
plain data to a pure builder. Nothing is persisted: the PDF is a projection of the current
rows, not a copy.

This keeps a single source of truth — a corrected line or a renamed supplier shows up on the
next download — and avoids a second table set with its own numbering, retention and
authorization rules. The trade-off is that a re-download can differ from the copy a supplier
already received; immutable archival (hash + stored bytes) stays out of scope until there is a
compliance requirement for it.

### 2. Pure model, thin renderer, tenant-scoped service

Three layers, each testable on its own:

- `purchase-document-model.ts` — no I/O, no pdf-lib. It maps rows to a
  `PurchaseDocument` (title, status label, watermark, meta rows, parties, lines, totals,
  notes, serials) and owns the arithmetic and the formatting, so totals are unit-tested
  without parsing PDF bytes.
- `purchase-documents.pdf.ts` — a generic A4 renderer over that model
  (`renderPurchaseDocument`). It handles pagination, column fitting, wrapping, page
  continuation headers, the watermark, and the footer.
- `PurchaseDocumentsService` — queries and 404 semantics; it owns no layout and no math.

The renderer is generic, so a third document type only needs a builder.

### 3. Totals round per line, then sum

Each line amount is `Math.round(quantity × unitCostMinor)` and the document total is the sum
of those rounded amounts. This matches what a reader can verify by adding the printed column,
and it mirrors the integer-millime discipline of the rest of the system: no floating-point
total that disagrees with its own rows.

A line without a unit cost has no amount. Those lines are excluded from the total, counted,
and flagged in a printed note, so a document with a missing cost never silently reads as
complete. Quantities keep up to four decimals, trimmed.

### 4. PDFs are plain A4 with standard fonts, sanitized to ASCII

The renderer embeds pdf-lib's `StandardFonts` (Helvetica, Helvetica-Bold, Courier for serials).
These are WinAnsi-encoded, so text is normalized first: diacritics are transliterated
(`Café` → `Cafe`), typographic quotes and dashes are mapped to ASCII, and anything still
outside printable ASCII becomes `?`. Money is formatted as ASCII dinars only
(`1,234.567 TND`), never with a locale-specific separator or symbol.

The limitation is explicit: a supplier name or product description written in Arabic will
print as question marks. Supporting it means embedding a Unicode font and shaping the script,
which is a separate decision; until then the ASCII document is correct for the Latin-script
data the system is used with.

Draft and cancelled documents carry a diagonal watermark, and every page carries
`Generated by MyStock on … UTC` plus `Page x of y`, so an outdated draft is never mistaken for
a final document.

### 5. Any member may download; non-members see a 404

Both routes live under the existing tenant path and run through `runAsMember`, so the reads
are RLS-scoped. Any role — including a viewer — can download, because a document is a read,
not a mutation. A caller who is not a member gets `404 organization_not_found`, and a document
id that does not belong to the organization gets `404 purchase_order_not_found` /
`404 purchase_return_not_found`, so neither organization nor document existence leaks.

### 6. Delivery is an attachment with an exposed filename

Responses are `application/pdf` with
`Content-Disposition: attachment; filename="mystock-<number>.pdf"` and an explicit
`Content-Length`. The API's CORS configuration exposes `content-disposition`, because browsers
hide it on cross-origin responses by default; without it the web client can download the bytes
but cannot read the server-chosen name. The web client saves the blob and uses that name.

## Consequences

- The printed document and the ledger always agree: both read the same rows, and the totals
  are computed from the same quantities the stock movements used.
- Corrections are visible immediately and never need a re-issue step, at the cost of no
  immutable archive.
- Supplier-facing text is limited to Latin script until a Unicode font is embedded.
- Still out of scope: goods-received notes, sales documents, signed or archived copies,
  e-invoicing, and any stored snapshot of a document as issued.
